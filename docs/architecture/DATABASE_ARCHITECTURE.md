## 2. Purpose

This document defines the production-grade database architecture for Kritva RaaS.

PostgreSQL is the authoritative persistent store for structured business and operational
state managed by the RaaS Control Plane.

The database provides durable state for:

- users;
- organizations;
- memberships;
- projects;
- platforms;
- platform versions;
- artifacts and artifact metadata;
- bookings;
- credit wallets;
- credit transactions;
- jobs;
- runs;
- labs;
- Lab Agents;
- resources;
- results metadata;
- audit records;
- idempotency records;
- configuration required for business operation.

The database does not store every type of data generated by the RaaS platform.

Large binary objects such as:

- `.krv` artifacts;
- video;
- large logs;
- telemetry exports;
- result files;

belong in object storage.

The database stores the metadata, ownership, lifecycle, integrity information, and
references required to manage those objects.

The central principle is:

    PostgreSQL
        = authoritative structured business state

    Object Storage
        = authoritative large-object content

    Queue
        = asynchronous work transport

    WebSocket
        = realtime notification transport

## 4. Goals

The database architecture shall:

1. Provide one authoritative business-state store.
2. Preserve strong transactional consistency.
3. Support multiple organizations.
4. Enforce tenant isolation.
5. Support concurrent bookings safely.
6. Prevent double credit consumption.
7. Prevent duplicate execution.
8. Support durable job state.
9. Support historical run records.
10. Support auditability.
11. Support efficient common queries.
12. Support controlled schema evolution.
13. Support production backups.
14. Support point-in-time recovery where available.
15. Support horizontal application scaling.
16. Keep large binaries outside PostgreSQL.
17. Maintain clear module ownership.
18. Support future data growth.
19. Keep application logic independent from storage implementation details.

## 5. Non-Goals

The database is not intended to:

- store customer source code by default;
- store large video files directly;
- store high-frequency raw telemetry indefinitely;
- act as a message queue;
- act as a WebSocket event bus;
- implement business workflows through database triggers alone;
- become a shared arbitrary SQL integration surface;
- expose database access to Studio;
- expose database access to Lab Agents;
- become a replacement for object storage;
- become a replacement for analytical/time-series infrastructure if future volume requires
  specialized systems.

## 6. Architectural Principle

PostgreSQL is authoritative for structured business state.

The architecture is:

    Control Plane
         |
         v
    Application Services
         |
         v
    Repository Interfaces
         |
         v
    PostgreSQL
         |
         +--> Users
         +--> Organizations
         +--> Projects
         +--> Platforms
         +--> Artifacts
         +--> Bookings
         +--> Credits
         +--> Jobs
         +--> Runs
         +--> Labs
         +--> Resources
         +--> Results
         +--> Audit
         +--> Idempotency

No external component should modify business tables directly.

## 7. Database Technology

PostgreSQL is the required relational database technology for the RaaS Control Plane.

The architecture should use a current supported PostgreSQL release approved for
production deployment.

The exact managed PostgreSQL provider and major version remain deployment decisions.

The application should avoid unnecessary dependence on provider-specific PostgreSQL
extensions.

Standard PostgreSQL functionality should be preferred unless a specific extension has
a clear architectural justification.

## 8. Logical Database Boundaries

The database is logically divided by domain ownership.

Recommended logical domains:

| Domain | Primary Data |
|---|---|
| Identity | users, identities |
| Organization | organizations, memberships |
| Project | projects |
| Platform | platforms, versions, capabilities |
| Artifact | artifacts, validations |
| Booking | availability-related state, bookings |
| Credit | wallets, plans, transactions |
| Execution | jobs, runs |
| Resource | labs, agents, resources, allocations |
| Result | results, result files metadata |
| Audit | audit events |
| System | idempotency, configuration, migrations |

These boundaries are logical even when deployed in one PostgreSQL database.

## 9. Schema Strategy

The initial implementation should favor a single PostgreSQL database with clear
module-owned tables.

A schema-per-module strategy may be introduced if it provides meaningful isolation.

The preferred starting model is:

    PostgreSQL Database
        |
        +--> identity tables
        +--> organization tables
        +--> project tables
        +--> platform tables
        +--> artifact tables
        +--> booking tables
        +--> credit tables
        +--> execution tables
        +--> resource/lab tables
        +--> result tables
        +--> audit tables
        +--> system tables

The application architecture, rather than PostgreSQL schema count, provides the primary
module boundary.

## 10. Schema Naming

Table names should be consistent and predictable.

Recommended convention:

- lowercase;
- snake_case;
- singular or plural convention selected once and applied consistently.

The project should standardize one convention before schema implementation begins.

For this architecture, plural table names are recommended.

Examples:

    users
    organizations
    projects
    platforms
    artifacts
    bookings
    credit_transactions
    jobs
    runs
    labs
    resources
    results
    audit_events

## 11. Primary Keys

Every persistent entity should have a stable primary key.

The recommended logical identifier is an opaque identifier such as UUID.

Identifiers should not encode:

- organization;
- timestamp;
- platform;
- user identity.

Opaque identifiers reduce accidental coupling between external API contracts and
database implementation.

## 12. External IDs

External/public resource IDs should normally correspond to stable opaque identifiers.

The database must not expose sequential integer IDs as security-sensitive public identifiers.

Database-generated internal identifiers may still be used where appropriate, but public
resource identity should remain stable and non-guessable.

## 13. Common Audit Columns

Most mutable business entities should include appropriate lifecycle metadata.

Typical fields:

    id
    created_at
    updated_at
    created_by
    updated_by
    version
    status

Not every table requires every field.

Audit requirements should be driven by domain semantics.

## 14. Timestamps

Timestamps should be stored consistently in UTC.

Recommended PostgreSQL type:

    TIMESTAMPTZ

The application should convert timestamps to user/local timezone only at presentation
boundaries.

## 15. Tenant Model

The RaaS platform is multi-tenant.

The primary tenant boundary is the organization.

Conceptually:

    Organization
       |
       +--> Members
       +--> Projects
       +--> Artifacts
       +--> Bookings
       +--> Credits
       +--> Jobs
       +--> Runs
       +--> Results

System-wide resources such as platform definitions and lab inventory may be global,
while tenant-owned records are organization-scoped.

## 16. Tenant Ownership

Tenant-scoped tables should carry an organization reference either directly or through
a controlled ownership relationship.

Examples:

    projects.organization_id
    artifacts.organization_id
    bookings.organization_id
    credit_wallets.organization_id
    jobs.organization_id
    runs.organization_id
    results.organization_id

The exact presence of organization_id may be omitted when ownership is unambiguously
derived through a parent entity.

However, direct tenant keys may be beneficial for authorization and query efficiency.

## 17. Tenant Isolation

Every tenant-scoped query must enforce organization boundaries.

The application must never rely solely on frontend filtering.

For example:

    SELECT ...
    FROM projects
    WHERE id = :project_id
      AND organization_id = :organization_id;

Repository methods should make tenant context explicit where required.

## 18. Row-Level Security

PostgreSQL Row-Level Security may be considered for defense-in-depth.

The baseline architecture does not require RLS if the application architecture already
provides strong tenant isolation.

If RLS is adopted, it must be implemented consistently across all tenant-scoped tables.

A mixed model where some sensitive tables use RLS and others rely on application checks
requires explicit review.

## 19. Tenant Isolation Invariant

The following must always hold:

    User
      |
      v
    Authorized Organization
      |
      v
    Authorized Entity

A user must never retrieve another organization's:

- project;
- artifact;
- booking;
- credit wallet;
- job;
- run;
- result.

## 20. Identity Data

Identity-related records include:

- user;
- external identity reference;
- account status;
- profile metadata.

Authentication credentials should normally remain with the selected identity provider.

The database stores only the application identity information required by the Control
Plane.

## 21. Organization Data

Organization records include:

- organization ID;
- name;
- status;
- created date;
- settings reference.

Membership records include:

- user;
- organization;
- role;
- status;
- created date.

Membership is a key authorization boundary.

## 22. Project Data

A project represents a logical customer development/execution workspace.

Conceptual data:

    projects
        id
        organization_id
        name
        description
        status
        created_by
        created_at
        updated_at

A project does not normally contain source files.

## 23. Platform Data

Platform records define execution targets.

Conceptual data:

    platforms
        id
        name
        status
        architecture
        runtime_family
        description

Related data may include:

    platform_versions
    platform_capabilities
    platform_sdk_versions
    platform_resources
    credit_plans

Platform definitions may be system-wide.

## 24. Platform Versioning

Platform compatibility must be version-aware.

A platform version may define:

- KritvaOS version;
- runtime version;
- supported architecture;
- SDK versions;
- capabilities.

This prevents a generic platform name from hiding compatibility differences.

## 25. Artifact Data

Artifacts represent signed execution packages.

Conceptual fields:

    artifacts

        organization_id
        project_id
        platform_id
        version
        format_version
        architecture
        runtime_version
        sdk_version
        checksum
        signature_metadata
        object_key
        size_bytes
        status
        created_at

## 26. Artifact Validation

Validation records may capture:

- validation attempt;
- validator version;
- compatibility result;
- signature result;
- checksum result;
- failure code;
- timestamp.

Validation history may be retained separately from current artifact status.

## 27. Booking Data

A booking represents an authorized reservation for a platform/resource and time range.

Conceptual data:

    bookings
        id
        organization_id
        project_id
        platform_id
        resource_id
        start_time
        end_time
        status
        credit_quote
        credit_reservation
        created_by
        created_at

## 28. Booking Conflict Protection

Booking conflicts must be prevented transactionally.

PostgreSQL range types and exclusion constraints may be considered for resource/time
overlap prevention.

A possible conceptual model is:

    resource_id + time_range

with an exclusion rule preventing overlapping confirmed reservations.

The final implementation should select the simplest reliable mechanism.

## 29. Credit Plan Data

Credit plans define commercial rules.

Conceptual fields:

    credit_plans
        id
        platform_id
        name
        type
        credits
        price
        currency
        validity
        status

The exact commercial model may evolve.

## 30. Credit Wallet Data

A wallet is associated with an organization and credit type/plan policy.

Conceptual fields:

    credit_wallets
        id
        organization_id
        platform_id
        credit_type
        balance
        status

## 31. Credit Transaction Data

Credit transactions should be immutable or append-oriented.

Conceptual fields:

    credit_transactions
        id
        wallet_id
        organization_id
        type
        amount
        reference_type
        reference_id
        created_at
        metadata

Transaction types may include:

    PURCHASE
    RESERVATION
    CONSUMPTION
    RELEASE
    REFUND
    ADJUSTMENT
    EXPIRATION

## 32. Credit Consistency

Credit changes must be transactional.

A credit-consuming operation must never:

- charge twice;
- create negative balance unintentionally;
- consume credits from another platform;
- lose the accounting reference.

The credit transaction and relevant business state should be committed consistently.

## 43. Idempotency Data

Idempotency records protect operations from duplicate requests.

Conceptual fields:

    idempotency_records
        id
        organization_id
        actor_id
        key
        operation
        request_hash
        status
        response_reference
        created_at
        expires_at

A unique constraint should protect the key within the appropriate scope.

## 44. System Configuration

Business configuration that must be durable may be stored in dedicated configuration
tables.

Examples:

- platform policies;
- credit rates;
- retention policies;
- feature configuration.

Operational secrets do not belong in ordinary configuration tables.

## 45. Repository Architecture

Repositories are the application boundary to PostgreSQL.

Examples:

    UserRepository
    OrganizationRepository
    MembershipRepository
    ProjectRepository
    PlatformRepository
    ArtifactRepository
    BookingRepository
    CreditRepository
    JobRepository
    RunRepository
    LabRepository
    ResourceRepository
    ResultRepository
    AuditRepository
    IdempotencyRepository

## 46. Repository Ownership

Each repository should primarily belong to one module.

A repository should not become a cross-domain query service.

Cross-domain data retrieval should use:

- application services;
- explicit query services;
- read models where necessary.

## 47. Repository Interface

Conceptually:

    interface ProjectRepository {
        create(project)
        getById(organizationId, projectId)
        list(organizationId, filter, page)
        update(project)
        archive(organizationId, projectId)
    }

The repository should enforce tenant context where appropriate.

## 48. Repository Transaction Context

Repositories should participate in application-controlled transactions.

Example:

    transaction {
        creditRepository.reserve(...)
        bookingRepository.create(...)
        auditRepository.append(...)
    }

The transaction boundary should be explicit.

## 49. Avoid Generic Repository Abstractions

The architecture should avoid a single generic interface such as:

    repository.save(anyEntity)

Such abstractions often hide domain semantics and make concurrency behavior unclear.

Domain-specific repositories are preferred.

## 50. Query Services

Read-heavy or cross-domain views may use dedicated query services.

Examples:

    DashboardQueryService
    JobHistoryQueryService
    PlatformAvailabilityQueryService

These services can use optimized SQL while maintaining a controlled application boundary.

## 51. Read Models

Read models may be introduced when:

- dashboard queries become expensive;
- multiple modules must be joined frequently;
- realtime views require optimized projection;
- analytical queries compete with transactional workloads.

The source of truth remains the normalized transactional model.

## 52. Transaction Principles

Transactions should be:

- short;
- explicit;
- atomic;
- bounded;
- retry-safe where appropriate.

Long-running operations must not hold database transactions while waiting for:

- object storage;
- Lab Agent;
- user input;
- external services.

## 53. Transaction Example: Booking

The booking transaction may perform:

    BEGIN
      |
      +--> Validate organization access
      +--> Lock relevant resource/availability
      +--> Check time conflict
      +--> Reserve credits
      +--> Create booking
      +--> Record audit
      +--> Record outbox/event state if used
      |
    COMMIT

External notifications should occur after commit.

## 54. Transaction Example: Job Creation

    BEGIN
      |
      +--> Validate project
      +--> Validate artifact
      +--> Validate booking
      +--> Validate credit reservation
      +--> Create job
      +--> Record idempotency result
      +--> Create scheduling request/outbox
      |
    COMMIT

The worker acts after the transaction commits.

## 55. Outbox Pattern

An outbox table may be used for reliable publication of database-backed events.

Conceptually:

    Transaction
       |
       +--> Business State
       |
       +--> Outbox Event
       |
       v
     COMMIT
       |
       v
    Outbox Worker
       |
       v
    Queue / Realtime

This prevents the failure mode where database state commits but event publication fails.

## 56. Outbox Scope

The outbox pattern is recommended for events that are critical to business workflow.

Examples:

- booking confirmed;
- credit transaction committed;
- job queued;
- artifact accepted;
- run completed.

Not every informational event requires an outbox record.

## 57. State Transitions

State changes should be explicit.

Examples:

    Artifact:
    CREATED -> UPLOADING -> VALIDATING -> ACCEPTED
                                      -> REJECTED

    Booking:
    CREATED -> CONFIRMED -> ACTIVE -> COMPLETED
                    \-> CANCELLED
                    \-> EXPIRED

    Job:
    CREATED -> QUEUED -> VALIDATING -> ALLOCATING
                                      -> DEPLOYING
                                      -> STARTING
                                      -> RUNNING
                                      -> STOPPING
                                      -> COMPLETED
                                      -> FAILED
                                      -> CANCELLED
                                      -> TIMEOUT

## 58. State Transition Validation

Application services should validate state transitions.

The database may enforce selected invariants through constraints, but business state
machines should primarily remain explicit in application/domain logic.

## 59. Optimistic Concurrency

Entities subject to concurrent updates may use a version column.

Conceptually:

    version = 7

Update:

    UPDATE jobs
    SET status = :new_status,
        version = version + 1
    WHERE id = :id
      AND version = 7;

Zero rows updated indicates a concurrency conflict.

## 60. Pessimistic Locking

Pessimistic locking may be used where contention is expected.

Examples:

- credit balance;
- resource allocation;
- booking slot;
- job state during critical transitions.

Locks must be held for the shortest practical duration.

## 61. Booking Concurrency

Booking is a high-risk concurrency operation.

The database must prevent:

    Request A --> available
    Request B --> available
    Request A --> create
    Request B --> create

when both overlap the same resource.

The final implementation should use PostgreSQL constraints and/or transactional
locking.

## 62. Credit Concurrency

Credit consumption must prevent:

    Balance = 100

    Request A consumes 80
    Request B consumes 80

Both must not succeed.

The database transaction must serialize or atomically validate the balance.

## 63. Resource Concurrency

A resource must not be allocated simultaneously to incompatible jobs.

Allocation must be protected by:

- unique constraints;
- transactional locking;
- allocation status;
- job/run state.

## 64. Indexing Strategy

Indexes should support:

- tenant filtering;
- primary relationships;
- lifecycle status;
- time ranges;
- recent activity;
- job lookup;
- run lookup;
- resource allocation.

Indexes should be driven by actual query patterns.

## 65. Core Indexes

Expected baseline indexes include:

    organizations
        primary key

    memberships
        user_id
        organization_id
        unique(user_id, organization_id)

    projects
        organization_id
        organization_id + status

    artifacts
        organization_id
        project_id
        platform_id
        status

    bookings
        organization_id
        resource_id + time
        status

    jobs
        organization_id
        project_id
        booking_id
        status

    runs
        organization_id
        job_id
        status

    results
        organization_id
        project_id
        run_id

## 66. Composite Indexes

Composite indexes should follow common query predicates.

For example:

    WHERE organization_id = ?
      AND status = ?

may justify:

    (organization_id, status)

Index order should reflect actual selectivity and ordering requirements.

## 67. Time-Based Indexing

Operational tables may need time-oriented indexes.

Examples:

    jobs(created_at)
    runs(started_at)
    bookings(start_time)
    audit_events(created_at)

Time indexes should be reviewed as data volume grows.

## 68. Partial Indexes

Partial indexes may be used for active-state queries.

Example concept:

    active resource allocations
    active bookings
    non-deleted artifacts

Partial indexes should be introduced based on measured query patterns.

## 69. Foreign Keys

Foreign keys should be used for important relational integrity.

Examples:

    project.organization_id
    artifact.project_id
    booking.platform_id
    job.artifact_id
    run.job_id
    result.run_id

Foreign keys should not create unintended deletion cascades for historical data.

## 70. Delete Policies

Default policy for important business entities should be conservative.

Examples:

- organizations: rarely physically deleted;
- projects: archive;
- artifacts: lifecycle/delete under policy;
- bookings: retain history;
- jobs: retain history;
- runs: retain history;
- credit transactions: never physically delete as normal operation;
- audit events: retain according to policy.

## 71. Cascading Deletes

Cascading deletes should be used sparingly.

They are generally inappropriate for:

- financial history;
- execution history;
- audit history.

A project deletion must not accidentally erase financial or execution records.

## 72. Soft Delete

Soft deletion may use:

    deleted_at
    deleted_by

where recovery/history is required.

Soft-deleted records must be excluded consistently from normal queries.

The application should avoid creating ambiguous semantics where a record is simultaneously
"deleted" and "active".

## 73. Database Constraints

Important invariants should be enforced at the database level where practical.

Examples:

- unique identifiers;
- unique membership;
- valid numeric ranges;
- non-negative quantities where appropriate;
- unique idempotency keys;
- unique active resource allocation.

## 74. JSONB Usage

JSONB may be used for extensible metadata.

Good candidates:

- capability metadata;
- platform metadata;
- diagnostic metadata;
- event metadata.

JSONB should not replace normalized columns for frequently queried business fields.

## 75. Metadata Policy

Structured business fields belong in typed columns.

Flexible metadata belongs in JSONB.

Avoid storing core authorization or financial state exclusively inside JSONB.

## 76. Database and Object Storage Boundary

The database stores:

    object_key
    content_type
    size
    checksum
    owner
    lifecycle_status

Object storage stores:

    binary_content

The database does not store the complete binary merely because PostgreSQL supports
binary data types.

## 77. Database and Queue Boundary

The database stores:

    job.status
    job.id
    job.state
    retry_count
    timestamps

The queue stores/transports:

    job_id
    operation
    message_id
    correlation_id

A queue message should be sufficient to locate authoritative state but should not
duplicate the complete business entity.

## 78. Database and WebSocket Boundary

The database stores:

    authoritative status

The WebSocket publishes:

    status changed

The WebSocket does not become the persistent event history unless an explicit event
store is introduced.

## 79. Event History

Where business history is required, store explicit records.

Examples:

- credit transactions;
- audit events;
- job state history if required;
- run state history where useful.

Do not assume that WebSocket events can reconstruct historical truth.

## 80. Audit History

Audit records should survive:

- application restart;
- queue restart;
- WebSocket disconnect;
- worker failure.

Audit history belongs in durable storage.

## 81. Migration Architecture

All schema changes must use version-controlled migrations.

A migration should:

- have a unique version;
- be reviewed;
- be tested;
- be applied deterministically;
- be tracked in the database.

## 82. Migration Naming

Recommended pattern:

    <version>_<short_description>

Examples:

    0001_initial_schema
    0002_add_platform_versions
    0003_add_artifact_validation
    0004_add_credit_transactions

The exact numbering system may vary.

## 83. Migration Ownership

Migrations belong to the backend/database source tree and must be deployed through
the controlled release process.

They must not depend on manual production SQL as the normal workflow.

## 84. Migration Testing

Every migration should be tested against:

- empty database;
- previous supported schema;
- representative production-like data.

Destructive migrations require additional review.

## 85. Backward-Compatible Migration

Preferred production pattern:

    Expand
      |
      v
    Deploy Compatible Application
      |
      v
    Backfill
      |
      v
    Switch Usage
      |
      v
    Contract

This allows application rollback during schema evolution.

## 86. Expand Phase

Examples:

- add nullable column;
- add new table;
- add new index;
- add new enum-compatible representation.

The existing application must continue working.

## 87. Backfill Phase

Large data migrations should be performed in controlled batches.

Do not hold a single transaction for millions of rows unless specifically justified.

Backfill jobs should be:

- resumable;
- observable;
- rate-limited;
- restart-safe.

## 88. Contract Phase

After all application versions no longer depend on old schema elements:

- remove deprecated column;
- remove obsolete index;
- remove old table;
- enforce new constraints.

Destructive changes should not occur in the same release as the initial dependency
introduction unless rollback is not required.

## 89. Zero-Downtime Migration

Production migrations should minimize:

- table locks;
- long transactions;
- blocking DDL;
- full-table rewrites.

Large indexes should use appropriate online/index-concurrently strategies where supported
and operationally safe.

## 90. Database Version Compatibility

The application must explicitly define the supported PostgreSQL major versions.

Upgrades should be tested in staging before production.

Managed PostgreSQL upgrades must have a documented rollback/recovery strategy.

## 91. Retention Architecture

Retention differs by data type.

| Data | Suggested Policy Direction |
|---|---|
| Credit transactions | Long-term |
| Audit events | Long-term |
| Bookings | Long-term |
| Jobs/runs | Long-term |
| Artifact metadata | Long-term |
| Artifact binaries | Policy-based |
| Results metadata | Long-term |
| Videos | Short/medium policy |
| Raw telemetry | Short/medium policy |
| Diagnostic data | Short policy |

Exact retention periods are product/compliance decisions.

## 92. Retention Enforcement

Retention should be automated.

Possible mechanisms:

- scheduled cleanup workers;
- PostgreSQL partition expiration;
- object-storage lifecycle policies.

Database cleanup must not violate audit, billing, or contractual retention requirements.

## 93. Partitioning

Partitioning should not be introduced prematurely.

Potential candidates at high scale:

- audit_events;
- telemetry metadata;
- job history;
- run history.

Partitioning should be introduced only when query/write volume demonstrates a need.

## 94. Audit Partitioning

If audit volume becomes large, time-based partitioning may be used.

Conceptually:

    audit_events_2026_10
    audit_events_2026_11
    audit_events_2026_12

Retention can then remove old partitions efficiently.

## 95. Telemetry Storage

High-frequency raw telemetry should not automatically be stored indefinitely in ordinary
transactional tables.

At scale, the architecture may use:

- time-series storage;
- object storage;
- compressed event files;
- specialized analytics infrastructure.

PostgreSQL should retain metadata and summarized metrics required by the product.

## 96. Database Backups

Production backups should include:

- automated full/snapshot backups;
- continuous WAL/PITR where supported;
- backup retention;
- encrypted backup storage.

Backup policy must align with RPO.

## 97. Point-in-Time Recovery

Where supported, PITR should allow recovery to a selected timestamp.

The recovery process must include:

1. identify recovery point;
2. restore database;
3. validate schema;
4. validate data;
5. reconcile application state;
6. reconnect application;
7. reconcile external systems.

## 98. Restore Testing

Restore testing must be periodic.

A restore test should verify:

- database can be restored;
- migrations are compatible;
- application can connect;
- critical records exist;
- indexes are valid;
- tenant isolation works;
- credit history remains consistent.

## 99. Backup Security

Backups must be:

- encrypted;
- access-controlled;
- isolated from application credentials;
- retained according to policy;
- monitored.

Production operators should not use unrestricted database credentials merely to inspect
backup state.

## 101. Database Recovery and Jobs

If the database is restored to an earlier point, execution state may differ from the
Lab Agent's actual state.

Therefore active jobs must be reconciled against Lab Agent state.

The database must not assume:

    restored job = robot stopped

## 102. Database Security

Database access must be separated by role.

Conceptual roles:

    application_runtime
    migration_runner
    read_only_operations
    backup_operator

The exact roles depend on the selected managed PostgreSQL service.

## 103. Application Database User

The application runtime should have only the privileges required for normal operation.

Schema modification privileges should not be granted to the normal application user.

## 104. Migration User

Migration operations should use a separate identity with schema modification privileges.

Migration credentials should be protected and used only during deployment.

## 105. Read-Only Access

Operational analytics and diagnostics should use read-only access where possible.

Direct production database queries should be audited.

## 106. Connection Security

Connections should use:

- TLS;
- certificate validation;
- managed network controls;
- secure credentials.

Database endpoints should remain private.

## 107. Connection Pooling

The application should use bounded pools.

If an external connection pooler is introduced, its transaction behavior must be validated
against:

- prepared statements;
- session state;
- transaction isolation;
- advisory locks;
- LISTEN/NOTIFY if used.

## 108. Isolation Levels

Default PostgreSQL isolation should be used unless a use case requires stronger semantics.

Possible requirements:

- booking conflicts;
- credit reservation;
- resource allocation.

Isolation decisions must be documented per transaction rather than globally increasing
isolation unnecessarily.

## 109. Lock Monitoring

Production monitoring should identify:

- long-running transactions;
- lock waits;
- deadlocks;
- idle transactions;
- connection exhaustion.

Deadlocks should be prevented through consistent lock ordering where practical.

## 110. Query Performance

The backend should monitor:

- slow queries;
- sequential scans;
- index usage;
- query latency;
- database CPU;
- connection count.

Performance optimization should be based on measured behavior.

## 111. N+1 Query Prevention

Repository/query services should avoid unbounded per-row queries.

Examples:

- project list with artifact counts;
- job list with platform names;
- run list with result status.

Use explicit joins or controlled batch queries.

## 112. Pagination Strategy

Large lists should use bounded pagination.

Offset pagination may be acceptable for small datasets.

Cursor/keyset pagination should be considered for:

- audit events;
- job history;
- run history;
- large artifact lists.

## 113. API Query Limits

The backend should enforce:

- maximum page size;
- maximum date-range queries;
- allowed filters;
- maximum sort options.

This protects PostgreSQL from expensive arbitrary queries.

## 114. Reporting Queries

Analytical/reporting queries should not degrade transactional workloads.

Options include:

- read replicas;
- materialized views;
- read models;
- analytics database;
- scheduled exports.

The initial product should keep reporting requirements modest.

## 115. Read Replica

A read replica may be introduced when:

- read traffic materially affects primary;
- dashboards require heavy queries;
- analytics load grows.

Critical transactional reads that require current state must remain on the authoritative
primary.

## 116. Database Observability

Database monitoring should include:

- CPU;
- memory where available;
- storage;
- IOPS;
- connections;
- transaction rate;
- query latency;
- lock waits;
- deadlocks;
- replication lag;
- backup status.

## 117. Data Integrity Checks

Periodic checks should validate:

- orphan records;
- invalid foreign references;
- negative/invalid credit states;
- active resource conflicts;
- inconsistent job/run states;
- missing artifact objects where detectable.

## 118. Reconciliation

A reconciliation worker may compare:

    PostgreSQL
        |
        v

        |

- orphaned allocations.

## 119. Object Reference Integrity

The database may contain an object key for a binary.

A reconciliation process should detect:

    DB says object exists
    but
    Object Storage says object missing

Such inconsistencies should produce alerts and recovery workflows.

## 120. Job State Integrity

The system should periodically identify impossible combinations.

Examples:

    job = COMPLETED
    run = RUNNING

or:

    resource = AVAILABLE
    active allocation exists

These indicate reconciliation defects.

## 121. Credit Reconciliation

Credit reconciliation should identify:

- balance mismatch;
- transaction duplication;
- missing transaction reference;
- invalid refund;
- consumption without associated job/run.

Financial-style data deserves stronger integrity checks.

## 122. Data Export

The platform may support export of user-owned data.

Exports should be generated asynchronously.

Large exports should be stored in object storage with controlled expiration.

The database provides authoritative metadata for the export.

## 123. Data Deletion

Deletion must consider:

- tenant requirements;
- audit;
- billing;
- execution history;
- retention;
- legal obligations.

A user-facing "delete project" operation does not automatically imply physical deletion
of all historical execution data.

## 124. Privacy

Sensitive user data should be minimized.

Do not store:

- source code unnecessarily;
- secrets;
- authentication passwords if identity provider owns them;
- unnecessary personal data.

The database should contain only information required for product operation,
security, billing, and audit.

## 125. Database Environment Separation

Each environment should have its own database.

    Development DB
    Staging DB
    Production DB

No application should accidentally connect to production using development credentials.

Seeds should include:

Production seed scripts must be tightly controlled.

## 127. Test Database

Automated tests should use isolated databases.

Tests should not depend on a shared developer database.

Database state should be reset or recreated predictably.

## 157. Database Architectural Invariants

The following invariants must remain true:

1. PostgreSQL is authoritative for structured business state.
2. Application code accesses PostgreSQL through controlled repositories/query services.
3. Studio never connects directly to PostgreSQL.
4. Lab Agents never connect directly to PostgreSQL.
5. Object binaries are not stored in ordinary business tables.
6. Queue messages are not authoritative state.
7. WebSocket events are not authoritative state.
8. Tenant isolation is enforced server-side.
9. Financial-style credit transactions are durable and auditable.
10. Booking conflicts are transactionally prevented.
11. Physical execution state is historically retained.
12. Migrations are version controlled.
13. Production schema changes are backward-compatible where practical.
14. Backups are tested through actual restore exercises.
15. Secrets are not stored as ordinary application data.
16. Large/high-frequency telemetry does not automatically become transactional PostgreSQL
    workload.
17. Historical records are not casually deleted.
18. Database failure must not be interpreted as robot safety state.
19. Active robot execution must be reconciled after database/cloud recovery.
20. Provider-specific database infrastructure remains outside domain logic.

## 159. Final Database Architecture Baseline

The Kritva RaaS database architecture establishes PostgreSQL as the authoritative
transactional foundation of the Control Plane.

The resulting architecture is:

    +----------------------------------------------------------+
    |                    RaaS Control Plane                    |
    |                                                          |
    |  Identity | Organization | Project | Platform            |
    |  Artifact | Booking | Credit | Job | Run                 |
    |  Lab | Resource | Result | Audit | Idempotency            |
    |                                                          |
    +--------------------------+-------------------------------+
                               |
                               v
                       Repository Boundary
                               |
                               v
                    +-----------------------+
                    |      PostgreSQL       |
                    |                       |
                    | Structured Authority  |
                    +-----------------------+
                         |             |
                         |             |
                         v             v
                  Transactions      History
                         |
                         v
                Business Integrity

Large data follows a separate path:

    Artifact / Video / Result / Log / Telemetry Export
                         |
                         v
                    Object Storage
                         |
                         v
                    Metadata in DB

Asynchronous work follows:

    PostgreSQL State
          |
          v
       Outbox
          |
          v
        Queue
          |
          v
       Worker
          |
          v
    PostgreSQL State Update

The database therefore remains the source of truth while other infrastructure provides
specialized capabilities.

The most important invariants are:

    PostgreSQL = truth
    Queue      = work
    WebSocket  = notification
    Storage    = large-object content
    Lab Agent  = lab boundary
    Robot      = real-time execution

The database must preserve correctness under:

- concurrent bookings;
- concurrent credit operations;
- duplicate API requests;
- duplicate queue messages;
- worker crashes;
- Lab Agent disconnection;
- application restarts;
- cloud outages;
- deployment changes;
- schema evolution;
- data growth.

The architecture deliberately favors strong relational consistency for business-critical
state while avoiding the use of PostgreSQL as a universal storage system.

The product's normal execution model remains:

    Source Code
        |
        | stays local
        v
    Local Build
        |
        v
    Signed .krv Artifact
        |
        v
    Cloud Object Storage
        |
        v
    Validated Job
        |
        v
    Lab Agent
        |
        v
    Robot Runtime
        |
        v
    Run
        |
        v
    Result Metadata + Objects
        |
        v
    PostgreSQL + Object Storage

This architecture gives Kritva RaaS a durable transactional foundation while preserving
clear boundaries between business state, large binary content, asynchronous processing,
realtime notification, and physical robot execution.

The database should remain intentionally boring, predictable, observable, recoverable,
and strongly controlled.

That is the desired foundation for a production RaaS platform.
