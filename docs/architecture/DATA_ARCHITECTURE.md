## 2. Purpose

This document defines the production-grade data architecture for Kritva RaaS.

The architecture establishes how data is:

- created;
- validated;
- owned;
- stored;
- transferred;
- transformed;
- observed;
- retained;
- archived;
- deleted;
- audited;
- recovered.

The architecture covers data generated by:

- RaaS Studio;
- Web Console;
- Control Plane;
- workers;
- Lab Agent;
- Kritva Runtime;
- robot hardware;
- telemetry systems;
- video systems;
- result collection.

The central principle is:

> **Structured business state belongs in PostgreSQL, large binary content belongs in object storage, asynchronous work belongs on durable queues, and high-frequency execution data is handled through purpose-specific storage paths.**

## 4. Goals

The data architecture shall:

1. Establish clear ownership for every important data domain.
2. Define authoritative sources.
3. Prevent duplicated conflicting sources of truth.
4. Protect tenant data.
5. Separate transactional data from high-volume data.
6. Keep large binaries out of PostgreSQL.
7. Preserve execution history.
8. Support reproducibility of experiments.
9. Support offline lab operation.
10. Support data reconciliation.
11. Provide auditable financial operations.
12. Support configurable retention.
13. Support data export and future deletion requirements.
14. Support multi-lab and multi-platform operation.
15. Provide a scalable path for telemetry and video.

## 5. Non-Goals

This document does not define:

- detailed PostgreSQL physical deployment;
- exact cloud provider;
- exact video codec;
- exact time-series database;
- detailed robot sensor schemas;
- detailed machine-learning data pipelines;
- source-code repository architecture;
- physical robot safety logic.

Those concerns are addressed by their respective architecture documents or future
platform specifications.

## 6. Data Architecture Principles

The architecture follows these principles:

1. One authoritative owner per business entity.
2. Durable business state is stored centrally.
3. Large files are stored outside PostgreSQL.
4. Queues transport work; they do not own state.
5. WebSocket transports events; it does not own state.
6. Local lab state is authoritative only for local physical/runtime state.
7. Cloud state is authoritative for business authorization and commercial state.
8. Data ownership follows domain ownership.
9. Tenant isolation is mandatory.
10. Execution data is traceable to a run.
11. Artifacts are immutable after acceptance.
12. Financial records are append-only.
13. Audit records are durable.
14. Retention is data-class specific.
15. Deletion must not destroy required audit or financial evidence.
16. Reconciliation is required where multiple stores represent related state.

Recommended classification:

| Class | Description | Examples |

## 10. Identity Data

Identity data includes:

- user ID;
- authentication provider reference;
- profile;
- email where applicable;
- account status;
- session metadata.

Authentication secrets should remain with the identity provider where practical.

The RaaS database stores only the information required for application identity and
authorization.

## 11. Organization Data

Organization data includes:

- organization ID;
- name;
- status;
- configuration;
- billing relationship;
- creation metadata.

Organizations form the primary tenant boundary.

## 12. Membership Data

Membership records define:

- user;
- organization;
- role;
- status;
- created time;
- updated time.

Membership changes are security-sensitive and auditable.

## 13. Project Data

Project data includes:

- project ID;
- organization ID;
- name;
- description;
- status;
- created/updated timestamps.

Projects are the logical container for application development and experiments.

## 14. Platform Data

Platform data describes robot classes.

Examples:

    humanoid-a
    humanoid-b
    mobile-base-a

Platform records may include:

- platform ID;
- name;
- version;
- architecture;
- capabilities;
- runtime requirements;
- supported artifact formats.

## 15. Resource Data

A resource represents an actual executable target.

Examples:

- robot-001;
- robot-002;
- simulation-001.

Resource data includes:

- resource ID;
- lab ID;
- platform ID;
- platform version;
- state;
- health;
- maintenance state;
- capabilities.

## 16. Lab Data

Lab data includes:

- lab ID;
- name;
- location metadata;
- operational status;
- configuration;
- connectivity state;
- safety qualification state.

Sensitive physical location information should be protected according to policy.

## 17. Agent Data

Lab Agent data includes:

- agent ID;
- lab ID;
- software version;
- protocol version;
- status;
- last heartbeat;
- registration metadata;
- capability summary.

Agent credentials themselves are not stored as ordinary database fields.

## 18. Artifact Data

Artifact metadata includes:

- artifact ID;
- project ID;
- organization ID;
- artifact version;
- platform;
- architecture;
- runtime requirement;
- SDK version;
- checksum;
- signature metadata;
- object-storage key;
- validation status;
- creation time.

The binary itself resides in object storage.

## 19. Artifact Immutability

Accepted artifacts should be immutable.

If an application changes:

    New build
       |
       v
    New artifact version

Do not overwrite the binary of an accepted artifact.

This provides reproducibility.

## 21. Booking Data

Booking records include:

- booking ID;
- organization;
- user;
- platform;
- resource/resource class;
- start time;
- end time;
- status;
- credit plan;
- quoted credits;
- consumed credits;
- cancellation information.

Booking records are authoritative in PostgreSQL.

## 22. Credit Data

Credit domain includes:

- credit plan;
- credit wallet;
- credit balance;
- credit transaction;
- reservation;
- consumption;
- refund.

Credits are platform-specific.

Example:

    Humanoid-A Developer Credits

The API must not treat platform-specific credits as a single generic balance.

## 23. Credit Ledger

Credit transactions should be immutable.

Example:

    CREDIT_PURCHASE
    CREDIT_RESERVATION
    CREDIT_CONSUMPTION
    CREDIT_RELEASE
    CREDIT_REFUND
    CREDIT_ADJUSTMENT

Current balance may be derived or maintained with transactional consistency.

## 24. Financial Data Governance

Financial data requires:

- stronger access controls;
- auditability;
- immutable transaction history;
- reconciliation;
- controlled deletion.

Financial records should not be casually deleted because they are no longer active.

## 25. Job Data

Job data represents an authorized execution request.

A job contains:

- job ID;
- organization;
- project;
- artifact;
- booking;
- resource;
- requested execution parameters;
- state;
- timestamps;
- idempotency reference.

## 26. Run Data

A run represents actual execution.

Run data includes:

- run ID;
- job ID;
- resource;
- artifact;
- execution instance;
- start time;
- end time;
- status;
- exit code;
- failure reason;
- metrics summary.

Run records provide the primary execution history.

## 27. Job and Run Relationship

Conceptually:

    Project
       |
       +--> Artifact
       |
       +--> Booking
               |
               v
             Job
               |
               +--> Run 1
               +--> Run 2
               +--> ...

Whether one job is limited to one run or supports multiple attempts is configurable,
but the data model must preserve execution identity.

## 28. Execution Data Authority

Cloud execution state:

    Control Plane
        = authoritative business execution state

Local runtime state:

    Lab Agent / Runtime
        = authoritative local execution observation

If they disagree, reconciliation determines the durable business state based on
observed local evidence.

## 29. Telemetry Data

Telemetry includes:

- CPU;
- memory;
- temperature;
- battery;
- joint state;
- velocity;
- sensor values;
- runtime metrics;
- application metrics.

Telemetry can be extremely high volume and should not automatically be stored in
PostgreSQL.

## 30. Telemetry Classes

Telemetry may be classified as:

| Class | Example | Typical Handling |
|---|---|---|
| Live | Current joint state | WebSocket |
| Short-term | Recent metrics | Time-series/buffer |
| Execution | Run metrics | Result/telemetry store |
| Summary | Min/max/average | PostgreSQL |
| Raw | High-frequency sensor stream | Specialized/object storage |

## 32. Telemetry Ownership

The Lab Agent is the initial collector.

The Control Plane owns the execution association.

A specialized telemetry system may become the storage owner for high-frequency
data.

## 33. Telemetry Sampling

Sampling may be applied to reduce data volume.

Examples:

    1 kHz local control data
        |
        v
    100 Hz diagnostic data
        |
        v
    10 Hz cloud telemetry

The exact rates are platform-specific.

## 34. Telemetry Retention

Telemetry retention should depend on:

- frequency;
- importance;
- experiment;
- customer plan;
- storage cost;
- safety/diagnostic requirements.

Raw high-frequency telemetry should generally have shorter retention than run summaries.

## 35. Telemetry Data Integrity

Telemetry records should include enough context to reconstruct meaning:

- run ID;
- resource ID;
- timestamp;
- metric name;
- unit;
- sampling information;
- source.

- booking policies;

    Current Platform Rate

        +--> Audit metadata

    Object Storage
        |
        +--> Artifacts
        +--> Result files

        +--> Recorded video

    Queue
        |
        +--> Work messages
        +--> Async processing

    Realtime
        |
        +--> WebSocket events

## 53. PostgreSQL Authority

PostgreSQL is authoritative for:

- identity references;
- organizations;
- projects;
- platform metadata;
- resource inventory;
- artifact metadata;
- bookings;
- credits;
- jobs;
- runs;
- result metadata;
- audit records.

## 54. Object Storage Authority

Object storage is authoritative for large immutable or semi-immutable files.

Examples:

    artifact.krv
    result.zip
    telemetry.parquet
    run-video.mp4
    logs.jsonl

The database stores references and metadata.

## 55. Queue Semantics

The queue is not authoritative.

A queue message may say:

    "Validate artifact X"

The authoritative artifact status remains in PostgreSQL.

If a queue message is lost or duplicated, the worker can reconcile from durable state.

## 56. WebSocket Semantics

WebSocket is not authoritative.

An event such as:

    job.running

means that a state transition occurred.

If the client misses it, the client queries:

    GET /api/v1/jobs/{job_id}

## 57. Studio-Local Data

Studio may maintain local data such as:

- source code;
- local build output;
- build cache;
- project metadata;
- credentials/session state;
- artifact package;
- local logs.

Source code remains local under the agreed build architecture.

## 58. Studio Source Ownership

Customer source code belongs to the user's local environment.

The initial RaaS platform does not require uploading source code.

Only the execution artifact crosses the cloud boundary.

## 59. Studio Sync Data

Studio synchronizes selected metadata:

- project;
- artifact;
- booking;
- job;
- run;
- result metadata.

It should not attempt to mirror the entire Control Plane database.

## 60. Lab-Local Data

The Lab Agent may maintain:

- agent identity;
- cached artifacts;
- active execution state;
- logs;
- telemetry buffers;
- result staging;
- local configuration.

This data is operational and must be bounded.

## 61. Local Cache Rules

Caches must not become hidden sources of business truth.

For example:

    Cached Booking
        !=
    Authoritative Booking

The Control Plane remains authoritative.

## 62. Offline Data Flow

       |

       +--> Log Buffer

## 64. Data Reconciliation

Reconciliation is required whenever state is represented in multiple locations.

Examples:

- job state;
- resource state;
- artifact upload state;
- result upload state;
- credit transactions;
- lab connectivity.

## 65. Reconciliation Principle

Reconciliation must use:

- stable IDs;
- timestamps;
- versions;
- checksums;
- execution identity;
- explicit state transitions.

It must not rely solely on arrival order.

## 66. Data Versioning

Data entities should include:

- created timestamp;
- updated timestamp where mutable;
- version where concurrent updates matter.

Immutable records such as credit transactions and audit events do not require mutable
versioning.

## 68. Tenant Isolation

Tenant-scoped data must include or inherit organization ownership.

The Control Plane must enforce tenant boundaries through:

- authenticated context;
- authorization;
- repository filtering;
- database constraints;
- tests;
- optional RLS defense-in-depth.

## 69. Cross-Tenant References

Cross-tenant references should generally be prohibited.

Shared public platform data is not tenant-owned.

A private organization's artifact cannot be referenced by another organization without
an explicit sharing mechanism.

## 70. Data Sharing

Future sharing may support:

- public artifacts;
- organization sharing;
- research collaboration;
- platform demonstration data.

Sharing must be explicit rather than implied.

## 71. Data Export

Users should eventually be able to export appropriate data.

Potential export:

- projects;
- artifact metadata;
- bookings;
- credit history;
- jobs;
- runs;
- results;
- selected telemetry;
- logs.

Exports should respect authorization and retention policies.

## 72. Data Deletion

Deletion must be classified by data type.

Examples:

    Project
       |
       +--> Soft archive
       |
       +--> Retention period
       |
       +--> Permanent deletion where permitted

Financial and audit records may require retention even after project deletion.

## 73. Soft Delete

Soft deletion may be used for business entities where recovery or auditability matters.

Examples:

- projects;
- artifacts;
- resources;
- configurations.

The API should hide deleted resources from normal queries.

## 74. Hard Delete

Hard deletion should be restricted to data classes where legally and operationally
appropriate.

Hard deletion must not break foreign-key or audit requirements.

## 75. Retention Policy

Retention should be defined by data class.

Initial policy framework:

| Data | Initial Retention Direction |
|---|---|
| Identity | Account lifetime + policy |
| Projects | Account lifetime + archive |
| Artifacts | Project lifetime + retention |
| Bookings | Long-term |
| Credit Transactions | Long-term |
| Jobs/Runs | Long-term operational history |
| Telemetry | Configurable |
| Debug Logs | Short/medium |
| Audit Logs | Long-term |
| Video | Configurable |
| Results | User/project policy |

Exact durations remain configurable.

## 76. Retention Governance

Retention policies must be:

- documented;
- configurable;
- auditable;
- enforced automatically;
- tenant-aware where necessary.

Retention changes should not silently delete historical data.

## 77. Legal Hold

Future governance should support legal or compliance holds.

A held record must not be deleted by normal retention processing.

## 78. Data Archival

Archival may move infrequently accessed data to lower-cost storage.

Potential candidates:

- old results;
- old telemetry;
- old logs;
- old video.

Archival must preserve references and checksums.

## 79. Data Purging

Purging is permanent deletion after retention expiry.

Purge workflows should be:

- automated;
- auditable;
- retryable;
- idempotent.

## 80. Object Lifecycle

Object storage lifecycle policies may transition:

    Active
       |
       v
    Infrequent Access
       |
       v
    Archive
       |
       v
    Delete

The lifecycle must remain consistent with database metadata.

## 81. Object Reconciliation

Periodic reconciliation should detect:

- database object reference with missing file;
- object with missing database reference;
- checksum mismatch;
- incomplete upload.

Such discrepancies should generate operational alerts.

## 82. Database Backup

PostgreSQL should use:

- automated backups;
- point-in-time recovery;
- backup monitoring;
- restore testing.

Backups are part of data architecture, not merely infrastructure.

## 83. Object Storage Backup

Critical object data requires:

- versioning where appropriate;
- replication or backup;
- deletion protection where required;
- restore validation.

## 84. Recovery Ordering

A recovery sequence may be:

    PostgreSQL
       |
       v
    Object Storage
       |
       v
    Queue
       |
       v
    Workers
       |
       v
    Control Plane
       |
       v
    Reconciliation
       |
       v
    Labs

The exact production procedure depends on deployment architecture.

## 85. Queue Recovery

Queue messages may be lost or duplicated during failures.

Durable business state allows workers to reconstruct required work.

Workers must be idempotent.

## 86. Data Encryption

Data should be encrypted:

- in transit;
- at rest.

Sensitive credentials require stronger protection.

Object storage and database encryption keys should be managed through approved key
management facilities.

## 87. Data Access Control

Access should follow:

    User
      |
      v
    Organization
      |
      v
    Project / Resource
      |
      v
    Data

Administrative access should be explicit and auditable.

## 88. Data Masking

Operational tooling should mask sensitive data where practical.

Examples:

- authentication identifiers;
- payment information;
- credentials;
- private configuration;
- security tokens.

## 89. Data Integrity

Integrity controls include:

- database constraints;
- foreign keys;
- checksums;
- immutable ledgers;
- signatures;
- object versioning;
- transactional updates.

## 90. Artifact Integrity

Artifact integrity uses:

    Artifact
       |
       +--> checksum
       +--> signature
       +--> metadata
       +--> immutable object

Both cloud and lab validation are required for critical integrity properties.

## 91. Result Integrity

Result files use:

- checksum;
- size;
- upload status;
- run association.

The result metadata must identify whether all expected files were successfully
persisted.

## 92. Financial Integrity

Credit operations require:

- atomic transaction;
- immutable ledger;
- idempotency;
- balance validation;
- reconciliation.

Audit data requires:

    long retention

    traceability

      v

      v

      v

      |
      v

The architecture must always preserve the relationship between data and the execution
that produced it.

The primary production principle is:

> **Every important piece of RaaS data must have a clear owner, an authoritative store, a defined lifecycle, a defined access policy, and a defined recovery strategy.**

This provides the data foundation required for Kritva RaaS to evolve from a single
development robot into a multi-platform, multi-lab Robotics-as-a-Service platform
without losing control of correctness, security, cost, reproducibility, or governance.
