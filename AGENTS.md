# Kritva RaaS Agent Instructions

These instructions apply to the `kritva-raas` repository (Kritva Robotic as a Service backend planning and, later, implementation). Read `planning/AGENT_RULES.md` first; this file adds the cross-repository rules and does not replace it.

## Boundaries

- Backend planning records live under `planning/backend/` (increment dossiers B-INC-001 to B-INC-004, task register, security gate). Keep dossiers, task register and test plan traceable to each other.
- `status/status.json` is generated by `scripts/status/gen_status.py` from the planning records. Regenerate it; do not edit it by hand. It reports 67 planning-only tasks.
- kritva-raas is not a baseline source in `kritva-program`. Nothing here creates program credit, and agents must not add this repository to the program's `sources.json` or approvals.
- Program-level decisions are recorded in `KritvaOS/kritva-program` (`v2/DECISIONS.md`), not here.

## Security gate

- SEC-GATE-001 (a credential-shaped loopback `DATABASE_URL` example found in history) has no recorded Security Owner disposition yet. Do not reintroduce credential-shaped examples; use clearly fake placeholders. Do not close or reclassify the gate; that is the Security Owner's decision.
- See `planning/backend/BACKEND_SECURITY_GATE.md`.

## Validation before a pull request

    python3 scripts/docs/check_docs.py
    python3 scripts/docs/check_backend_traceability.py
    python3 scripts/lint/check_source_headers.py --mode tracked --strict
    make status-gen-check

## Secrets and data

- Never commit credentials, tokens, private keys, production data or personal data. Use obviously fake values in examples and mark them as such.
- If a secret is committed by mistake, tell the Security Owner (Dinesh, D-032) at once. Removing it in a later commit does not make it safe; it must be revoked or rotated.
- The `secret-scan` workflow (gitleaks) runs on every push and pull request. Do not add allowlist entries to silence it; propose them to the owner with the reason.

## Commits and pull requests

- Work on a branch and open a pull request. Do not push to `main`. Do not force-push shared branches or rewrite history without the owner's explicit approval.
- Use short imperative messages in the repository's existing style (`type(scope): summary`).
- Do not add `Claude-Session:` or session-URL trailers to commit messages or pull request descriptions. The `commit-message-check` workflow rejects them. A `Co-Authored-By:` line is allowed.
- `main` is protected by a ruleset that requires `secret-scan`, `commit-message-check` and Code Owner review (owner statement, D-040; not independently verified). With one owner, the PR author cannot self-approve: ask the owner to merge using the bypass or add a second reviewer.

## When unsure

Say what you do not know and ask the owner. Do not invent evidence, test results, hardware behaviour or approvals, and do not claim a check passed unless you ran it.
